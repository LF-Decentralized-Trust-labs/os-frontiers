## Definitions used (quoted; full text in `top100-method.md`)

- **dOSPO** (dOSPO whitepaper §3): "A dOSPO is a community-mandated coordination layer that separates policy authority from operational execution in order to steward open source infrastructure within decentralized Web3 ecosystems. It derives legitimacy from decentralized governance and operates through a neutral, replaceable execution function constrained by explicit mandate." Also: "A dOSPO is explicitly not a foundation, a DAO, or a corporate OSPO under a different name."
- **OMF** (`sources/omf-whitepaper.txt` l.195–199; OMF WP p.5): "OMF is a portable operational architecture for sustaining decentralized open source infrastructure. It is designed to operate independently of any specific governance structure and can be executed by foundations, DAOs, elected committees, or independent operators. In ecosystems that adopt coordination bodies such as a Decentralized Open Source Program Office (dOSPO), OMF functions as the execution layer." **Minimum Viable OMF** (OMF WP p.15): "An ecosystem has implemented OMF if it has all five of the following": 1 dependency audit capability · 2 program governance authority · 3 at least one sustainment program · 4 transparent reporting mechanism ("at minimum on a quarterly basis") · 5 portfolio review cadence. (Spec only, not the definition: `omf/START_HERE.md` 5-Requirement Compliance Bar.)
- **ORF** (`sources/orf-whitepaper.txt` l.50–51; ORF WP p.2, Author's Note): "the ORF defines the replenishment layer (how resources come back)". Revenue families (ORF WP §8): A Structural Network Revenue · B Enterprise Earned · C Membership & Certification · D Voluntary & Pledges · E Capital Income. **Minimum Viable ORF** (ORF WP p.18): 1 verified cost floor · 2 classified inflow inventory ("Issuance and routing are excluded from replenishment totals") · 3 at least one earned instrument "collecting real receipts … measured on net contribution" · 4 net-contribution reporting (quarterly) · 5 ratio and gate review cadence. (Spec only, not the definition: `orf/START_HERE.md` §1 "a governance and economic design framework…"; INSTRUMENT_CATALOG A.4 "CANNOT count toward non-inflationary self-sustainability metrics".)
- **POSM stage** (`chains/posm-cycle-chain-map.md` §2.1 and §4 legend): P1 Funding In · P2 Steward Governance & Programs · P3 Outputs · P4 Commercialization Channels · P5 Commercial Adoption · P6 Return to Treasury. Placement = "the furthest POSM stage reached through a connected, evidenced path; a link to LEAK means value generated at P5 leaves without returning."

**Rating rules (aligned to `chains/top100-qa-rubric.md` v1.0 §B, which quotes the whitepapers):**
- **dOSPO-like.** Present = (i) community mandate, (ii) policy/execution separation, (iii) replaceable operator and (iv) time-bounded or renewable charter, all sourced. Partial = some of (i)–(iv), named in the cell. Missing = foundation or company alone, or a token vote on monetary parameters only.
- **OMF-like.** Present = a recurring, authorized maintenance-deployment program on a High-confidence row (rubric C7). Partial = one-off or episodic grants only, or programs without reporting. Missing = nothing, or only VC, accelerator, SAFE, buyback or burn. Each OMF cell lists which Minimum Viable OMF items (OMF WP p.15: 1 dependency audit · 2 program governance authority · 3 ≥1 sustainment program · 4 transparent reporting at least quarterly · 5 portfolio review) are shown.
- **ORF-like.** Present = a non-issuance, recurring inflow (Families A, B, C, E, or D pledges) flowing back to an OSS-maintenance treasury, named and sourced. Partial = collection exists but is not routed to maintenance, is not net-accounted, or is issuance (excluded; rubric C2 example: Zcash). Missing = no collection, or only burns, validator income, grants, drawdown, or issuance not aimed at OSS. **Grants alone or issuance alone are never Present.**
- **POSM.** P6 is never counted as reached when the return is issuance-dominated (rubric C5).
**"Would adding them help? (PROPOSAL)"** cells are **proposals, not findings**. Each suggests only plugging a real, named program or incentive into OMF or ORF **exactly as the whitepaper defines it**, with the section cited, labeled "Example". None suggests changing the model.
